KV cache 書籤：為什麼重試會火上加油

2026-08-26 · lazy-teach 微課 · local-llm

事發現場

Qwen3.8-27B 本地除錯現場：輸出無限循環。log 裡躺著一條鐵證——而客戶端的自動重試，正在悄悄拆自己的台。

事故當時，那個 slot 的 KV cache 已經揹著 172,573 tokens 的歷史（log 鐵證）。Hermes 重試時會微調訊息內容（追加錯誤說明、重新包裝），導致新請求和舊快取的「共同前綴」對不齊。

那個洞

llama-server 收到長請求時，會把每個 token「讀懂」的中間結果存起來——這就是 KV cache。下一個請求進來，它做一件事：從第一個 token 開始逐字比對，一模一樣的開頭直接沿用舊功課，只算新增的部分。這個能比對的開頭叫共同前綴。它像一本讀到一半的書夾了書籤：只要前面的字一模一樣，翻開就能續讀；任何一個字不同，書籤作廢，從那一頁起重算。

沿用靠逐字比對共同前綴：第一個不同的字之後，所有位置的理解都建立在錯的前文上，只能整段重算。
自動重試為什麼會火上加油？
心裡答完再點開
重試時客戶端會追加錯誤說明、重新包裝訊息——善意的小修改正好切斷前綴，快取全滅，輸出更慢更長，退化更嚴重。

回憶測驗

server 收到新請求時，決定哪些快取能沿用的機制是？

目標：判斷快取能否沿用。常見錯誤模式：以為 server「聰明地」記得語意——它只認位元組級的一模一樣。下一步：回去看事發現場那句「對不齊」，現在應該能自己講出機制。

172,573 tokens：歷史這麼長，代表 prefill 快取已是最大資產——打掉一次，重算代價以分鐘計。
微調訊息內容：重試的好意修改正是前綴殺手——任何一個字的差異都從那裡切斷沿用。
共同前綴：快取沿用的唯一通行證：新舊請求開頭逐字一致的部分。
